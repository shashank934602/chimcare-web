## What the template changed

The trial route was rebuilt against `send-to-client/spokane.html` partway through this run, so stage 6
has a before and an after on the same 100 URLs.

| Check | Before | After |
| --- | --- | --- |
| `canonical_present` | 0 pass · 100 fail | **100 pass** |
| `jsonld_present` | 0 pass · 100 fail | **100 pass** |

The `single_h1` failures were the trial route's own doing: it emitted a hero `h1` and then rendered

heading is the only `h1` on the page.

## The two checks that are not clean

**`description_present` — 66 pass, 34 fail.** This is a source-data fact, not a migration failure.
Of the 100 WordPress records, 66 stored a Yoast meta description and 34 stored none. All 66 that
existed migrated across intact, which `description_matches_source` confirms at 66 pass and 0 fail.
Nothing was invented for the other 34. **66 is the ceiling, and the migration reached it.**

Source coverage across the whole set:

| Yoast field | Records that had one |
| --- | --- |
| `yoastMetadesc` | 66 of 100 |
| `yoastTitle` | 0 of 100 |
| `yoastCanonical` | 0 of 100 |

No page in this sample had a stored SEO title or canonical, so `title_matches_source` is `n/a` on all
100. Titles come from the page's own `post_title` instead.

**`heading_order` — 77 pass, 23 fail.** Traced to the application's global footer, not to migrated
content and not to the template. `components/chrome/Footer.tsx` renders `<h4>` headings ("Services",
"States served", "Contact") with no `h3` above them, so any page whose body stops at `h2` shows a
level skip. The migrated bodies themselves are well ordered: the sampled failing page has source
heading levels `[1, 2, 2, 2, 2, 2, 2]` and no skip of its own.

Fixing this means changing the footer's heading levels, which is a change to shared site chrome and
outside what this trial should touch.

## Reproducing it

```bash
python3 scripts/stage1_select_urls.py --pattern '%-in-%' --exclude-regexp='-in-[a-z]{2}$' \
        --limit 100 --run family-a-100
python3 scripts/stage2_validate_status.py
python3 scripts/stage3_fetch_content.py
python3 scripts/stage4_build_routes.py --tag family-a-100 --emit-shard --emit-sql
npm run dev            # in the application, separate terminal
python3 scripts/stage5_test_render.py
python3 scripts/stage6_check_seo.py
```

Note the `=` in `--exclude-regexp=…`. The value begins with a dash, and without the `=` it is read as
a flag rather than a value.

## Second pass · images carried, pages on `/location/`

Two decisions changed after the first pass: images are carried rather than stripped, and the pages
moved from `/migration-trial/` onto the real `/location/` path, served by the existing dispatcher as
a fallback when the database has no row for a slug.

### Where the pages are served from

| Served by | URLs |
| --- | --- |
| The migration manifest | 97 |
| The database, which already had rows | 3 |

The three are Minnesota URLs. This matters for reading any number below: a database-served page never
touched the manifest, so measuring manifest coverage against it is meaningless. Stage 5 now detects
which branch answered, by looking for the marker class the manifest template carries, and reports
coverage as not applicable rather than as a failure. Before that fix those three read as the only
three failures in the run, which was wrong.

### Stage 5 · render

All six checks pass on all 100. Manifest coverage across the 97 manifest-served pages: minimum 0.806,
mean 0.957.

The old `no_images` check asserted that no image reached the page, which was correct when images were
stripped and became exactly backwards once they were carried. It is now `images_present`: every image
the manifest holds for a page must appear in the rendered HTML, because a silently dropped image is
the failure worth catching — the page still renders without it.

### Stage 6 · SEO

| Check | Result | Reading |
| --- | --- | --- |
| `canonical_present` | 100 pass | closed by the template |
| `single_h1` | 100 pass | closed by demoting source h1s |
| `jsonld_present` | 97 pass, 3 fail | the 3 are the database-served pages, which emit none |
| `images_have_alt` | 87 pass, 13 fail | 13 hero images have an empty alt in WordPress |

**`heading_order` fails on every page for a single reason.** The booking card is the application's own
component and emits `<h3 id="book-title">Schedule Your Chimney Service Today !</h3>` inside the hero,
directly after the `h1` and before any `h2`. Every page that embeds it therefore skips a level. This
is not caused by the migration: the database-served pages show the same `h1 → h3` sequence, so it
predates this work and affects the existing site equally. Fixing it means changing the shared
component's heading level, which is a decision about site chrome rather than about this trial.

**The 13 empty alt attributes are what WordPress stores.** They are left empty. An invented alt would
be a lie about the image, and an empty alt is a real signal that an image is decorative — though on a
hero photograph it is more likely an oversight in the source than a decision.

### What the automated checks could not see

Every page passed every render check in the first pass while the rendered result still had large empty
bands where the reference design expects photography. No check in this pipeline can see an empty band.
That gap was found by looking at a screenshot, and it is the reason images were carried.

## Fourth pass · the service directory

The reference's `o1-solutions` section carries a service directory: category chips filtering a grid of
cards, eight at a time, with a "Showing X of Y" line. It was dropped when the two templates were
unified, which also cost each page a great deal of internal linking.

The application already had the component. `components/islands/ServiceDirectory.tsx` is a faithful
React port of the reference's filter script, and `data/seed/services.ts` holds the same 8 categories
and 92 services with per-category counts identical to the reference. Restoring it was wiring, not
building.

### Only services that exist

A card renders only where that service has a published WordPress page for that city, so every card
links to a real page. A city with no service pages shows no directory at all rather than an empty one.

| | |
| --- | --- |
| Real internal links across the 100 pages | 3,477 |
| Services per page | 0 to 92, median 24 |
| Pages with no directory | 18 of 100 |
| Pages linking to themselves | 0 |

The resolution runs one query per city rather than per page: 68 queries cover the 100 pages. Links come
from the database saying a page is published, not from probing each URL over HTTP. Probing 3,477 URLs
would be a different kind of run, and the distinction is recorded rather than glossed.

The slug parser splits on the FIRST `-in-`, because no service key contains that string. That keeps a
city such as Lake in the Hills intact instead of truncating it. A slug whose tail is not a two-letter
state gets no directory rather than a wrong one.

### The counts tell the truth

The reference prints "All 92 services" in its reset chip. On a city with 24 published pages that would
be a claim the data does not support, so the chips and the status line report the count for that page.
The layout matches the reference; the number matches reality.

## Fifth pass · the accordion standardised, the body cut, the FAQ swapped in, two checker bugs

### The service accordion

It used to build one row per level-3 heading in the migrated body — 20+ rows on a typical page. It
now renders the reference's own eight entries: Chimney Sweeping, Inspection, Repair, Masonry Repair,
Leak Repair, Creosote Removal, Flue Cleaning, Tuckpointing — each with a summary, two paragraphs, a
four-item "What's included" list and a CTA. None of that is per-page copy any more.

Two sentences were dropped rather than carried, because they make climate claims that are false on
the Arizona and Georgia pages in this run: the Spokane "October through March … leading cause of
chimney fires" sentence, and "heavy snow loads, months of freezing temperatures and wet springs". A
third Spokane-only reference, the "Browne's Addition" neighbourhood, became a city slot instead. Every
drop is recorded in a `droppedSentences` audit field.

### The migrated body is no longer rendered

The page shows the body's opening group and nothing after it. Measured across the 100 pages: a median
93% of each body is not rendered (range 60% to 99%), 201,267 words total, leaving a median of 110
source words on a page. Nothing is deleted — the full body, its raw bytes and its SHA-256 stay in
`out/03-content.json`. Stage 4 now records the split per route as `renderedBlocks` and
`archivedWords`.

The consequence stated plainly: with most of the unique text gone, these hundred pages are largely
one template plus a catalogue, which is the classic shape of a duplicate-content problem in search.
This is a trade the design chose, not something the pipeline discovered.

### The contact section is now the reference's FAQ

Seven questions. The seeded Minnesota FAQ was dropped because three of its topics were the same
questions in different words.

Two guards were checked. The question quoting $299 and $69 renders only where a real region price
resolves and is omitted entirely otherwise — verified on Afton (database-sourced, shows it) against
Burlington and St Paul (manifest-sourced, do not; no dollar sign appears anywhere in their visible
text). A climate sentence about burning through a winter was dropped for the same reason as the
accordion sentences above. `FAQPage` JSON-LD is built only from the questions actually rendered.

### Two bugs in the pipeline's own checker

Coverage fell to 27/100 before these were found, and both were the checker's fault, not the render's.

- `lib/content.py` decoded decimal HTML entities but not hex, so React's `&#x27;` never became an
  apostrophe and every paragraph containing one looked absent. Fixing it took coverage 27 → 68.
- Stage 4's rendered-cut rule cut at the second LEVEL-2 heading, which kept two heading groups on any
  page whose body opens with an h1 — 32 of the hundred — and scored those extra blocks as missing from
  a page that never meant to show them. Cutting at the second heading of any level took it to 100/100.

The gate was restored by fixing the checker, not by loosening the threshold.

## Sixth pass · the service-area rail, a checker bug, a fresh stage 6

### The service-area band became a two-row rail

Always two rows, so a city with forty areas cannot make the band ten rows tall. Under 6 areas it
collapses to a single row. Arrows appear only from 12 areas up, and only when the rail actually
overflows — measured in the browser, not assumed from the count. Chips show at most two words with an
ellipsis; the full name stays available to screen readers and crawlers. Every chip is server-rendered;
the client island adds only the arrows.

### A bug found and fixed in that work

The two-word truncation initially rendered the full name a second time for screen readers even when
nothing was truncated, so every chip carried its name twice in the text layer. The hidden copy now
appears only when the visible form is actually clipped.

## Seventh pass · the pipeline gets a database

The pipeline stored its work as a chain of JSON files. At 1,000 URLs `out/03-content.json` reached
32 MB and `out/04-routes.json` reached 15.1 MB, which extrapolates to 320 MB and 151 MB at 10,000,
and 6.2 GB and 3.0 GB at 200,000. Worse, the Next.js page parsed the whole route manifest on every
request to find one slug — a migration manifest treated like a database while read like a text file.

It now uses one local SQLite database, `out/migration.sqlite`: one table per stage, `slug` as the
primary key throughout — `urls`, `status`, `content` + `services`, `routes`, `render`, `seo`, plus a
namespaced `meta` table. What changed and why:

- **Indexed lookup.** The application runs `SELECT ... WHERE slug = ?` and reads one row per request
  instead of parsing a whole manifest.
- **WAL mode.** The pipeline writes while the dev server reads. In WAL a reader never observes a
  half-committed transaction, so a torn read is impossible at the source rather than something every
  reader has to recover from — which is also why no temp-file-and-rename dance is needed.
- **Bodies stored once.** The raw WordPress body lives zlib-compressed in `content.body` and nowhere
  else; the route payload carries the blocks the page renders, not the original body.
- **Resumable.** Each stage takes its work from the previous stage's rows minus its own, so a run
  that dies at 9,000 of 10,000 does not re-request those 9,000. Stages 2, 3, 5 and 6 all have it —
  exactly the stages that make network or database calls.
- **Prunable.** `prune()` drops the raw bodies when a run is done, since they are the bulk of the
  file and re-running stage 3 restores them.
- **Local, not hosted.** This is a build artifact, not production data: deleting it must restore
  database-only behaviour, and the project's own rule is that the pipeline never writes to the
  application's database. Supabase's free plan also caps at 500 MB, which this workload passes at
  roughly 15,000 of the 200,000 URLs; the Pro plan's 8 GB would fit but means a network round trip
  per page render for an artifact that only exists while the trial runs. Hosted Postgres is the right
  place for the eventual cutover, not for staging the pipeline's own work.
- **Corrupt artifact ≠ broken site.** A missing or unreadable store means the application falls back
  to database-only behaviour and an unknown slug 404s.

JSON artifacts are still written for runs at or under 2,000 rows as a convenience; above that the
database is the artifact.

No timed 1,000-URL run has been completed since this refactor, so no throughput figure is quoted
here yet.
